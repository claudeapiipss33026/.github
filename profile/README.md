<p>静态住宅 IP 的难点不在买，而在用。地址固定下来之后，真正决定成败的是接入方式、监控基线和故障切换顺序。这篇按时间线走：上线前一周要定什么、上线当天怎么验、第一个月盯哪些指标、三个月后复核什么、出事时先动哪一步，每一步都给可执行的检查项和通过标准。</p>

<h2>一、上线前一周：把账号、出口、密钥三件事定下来</h2>
<p>很多问题在写第一行代码之前就埋下了。这一周的目标不是跑通，而是把不可逆的决定先做完，避免上线后推倒重来。</p>
<h3>账号与出口的绑定关系先画出来</h3>
<p>一个账号对应一条出口，还是一组账号共用一条？这个决定影响后面的扩容方式和故障半径。用一张表把账号、环境、出口、负责人四列写清楚，比放在脑子里可靠。表里再加一列变更记录，谁在什么时候动过哪条线，一目了然。</p>
<h3>密钥与出口分开管理</h3>
<p>密钥放在环境变量或密钥管理服务里，不要写进代码仓库；出口配置放在独立的配置文件或网关注入。两者分离，换出口时不用动代码，轮换密钥时不用碰网络。这一条在出故障时能省掉大量排查时间。</p>
<h3>确认目标地区的可用性</h3>
<p>先去官方文档核对服务在目标地区是否可用，再看出口所在国家是否落在支持范围内。这一步不做，后面所有调试都可能白费。同时确认账号所在组织的资料是否完整，信息缺失会让某些请求直接被拒。</p>

<h2>二、上线当天：代理接入与首轮连通性验证</h2>
<p>上线当天的验证要覆盖三层：网络通、协议通、业务通。三层分开测，出问题时才知道卡在哪一层，而不是笼统地判断线路不行。</p>
<h3>网络层：出口地址是否如约</h3>
<p>用 curl 查一次出口地址，比对订单里的地址清单。再看 ASN 是否属于住宅运营商，类型标签是否被标为托管。三项一致才继续往下，任何一项不符先找供应商确认，不要自己想办法绕。</p>
<h3>协议层：TLS 与长连接是否正常</h3>
<p>测一次完整握手，记录握手耗时；再发一个流式请求，确认数据能持续返回而不是等到最后一次性吐出。流式断流是静态出口最常见的问题之一，多发生在中间设备上，表现为前几秒正常、后面卡住不动。</p>
<h3>业务层：用小流量跑通全链路</h3>
<p>用真实请求体发十条，检查返回内容、耗时分布、错误码。十条全过不代表稳定，但能排掉配置类错误。这时候再看一眼超时设置是否与真实响应长度匹配，不匹配就当场改掉，别留到线上再发现。</p>

<h2>三、运行首月：监控项与基线建立</h2>
<p>第一个月的任务是建立基线。没有基线，后面所有的变慢了、不稳定了都只能是感觉，没法判断是不是真的退化，也没法向同事解释为什么要换线路。</p>
<h3>四个必采指标</h3>
<p>成功率、P95 延迟、超时率、出口变更次数。四个指标按小时聚合，存够三十天。不要只存平均值，P95 才能反映真实体感——平均值好看而 P95 很难看的线路，用起来一样难受。</p>
<h3>基线要分时段，告警阈值设在基线之上</h3>
<p>白天和晚高峰的基线分开记。把两者混在一起算平均，会得到一个谁都不满意的数字；分时段之后，晚高峰的退化能被立刻看出来。告警阈值用基线推：成功率低于基线的九成、P95 延迟超过基线的 1.5 倍就触发。拍脑袋定阈值，要么天天响，要么永远不响。</p>

<h2>四、三个月后：容量复核与地址体检</h2>
<p>静态不等于一劳永逸。地址会被动积累信誉记录，业务量也在变，定期复核是必须的动作，而且最好固定成日历上的一个日程。</p>
<h3>容量按峰值重算</h3>
<p>用过去九十天的峰值并发乘以 1.3，和当前配置比。低于这个数就该扩容。注意重试会放大并发，计算时把重试倍数算进去，否则扩容之后仍然会在高峰期排队。</p>
<h3>地址信誉与配置漂移一起查</h3>
<p>重新查一次 ASN、类型标签、近九十天的滥用投诉。静态地址长期使用后，如果同段被他人做了不当操作，信誉可能被动下降。同时把当前配置和上线时的版本对比一次，三个月里总有人改过超时、改过重试次数，漂移的地方要么写回文档，要么更新基线。</p>

<h2>五、故障发生时：切换顺序与回滚步骤</h2>
<p>故障时最忌讳边查边改。先按固定顺序切到备用，再回头定位原因，顺序错了会把两个问题叠在一起，排查难度成倍上升。</p>
<h3>第一分钟确认影响面，第三分钟切备用</h3>
<p>看监控面板，是全链路失败还是单节点失败、是全部账号还是个别账号。影响面决定了是切备用还是只重启单个实例。备用出口平时要保持热备，至少每周跑一次真实流量，否则切过去才发现配置过期。切换动作要写成脚本，不要临时手工改。</p>
<h3>恢复后补记录再复盘</h3>
<p>把故障时间、影响范围、切换动作、根因写进记录。没有记录的故障会重复发生，这是运维里最确定的一条规律。复盘时重点看两件事：告警是否及时、切换是否按脚本执行，而不是追责。</p>

<h2>常见问答</h2>
<h3>静态住宅 IP 真的不会变吗？</h3>
<p>答：合同期内通常不变，但上游网段调整、运营商策略变化都可能导致变更。要在合同里约定变更通知义务，并自己每周记录一次出口地址做比对。</p>
<h3>一个静态出口能给几个账号用？</h3>
<p>答：技术上可以多个，管理上建议一个。多个账号共用一条出口，行为会互相影响，出问题时也无法区分责任。账号数量多就按组分配，而不是挤在一条线上。</p>
<h3>需要配备用出口吗？</h3>
<p>答：看业务对中断的容忍度。有订阅续费、支付类动作的业务，建议配一条不同上游的备用线；纯内部工具可以只做重试，不必常备。</p>
<h3>监控用什么工具？</h3>
<p>答：轻量场景用定时脚本加告警机器人即可，需要看板就用 Prometheus 加 Grafana。工具不是关键，关键是四个指标按小时存够三十天。</p>
